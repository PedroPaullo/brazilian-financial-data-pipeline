# Deploy no Railway\n\n## Arquitetura publicada\n\nO serviço principal usa o Dockerfile e inicia src.railway_entrypoint:\n1. executa a carga inicial somente quando o SQLite ainda não existe;\n2. inicia a API FastAPI na porta fornecida por PORT;\n3. inicia o scheduler em processo separado;\n4. coleta e processa os dados em dias úteis às 07:00 no fuso America/Sao_Paulo;\n5. mantém data, reports e logs no volume persistente do Railway.\n\nO health check é GET /health.\n\n## Configuração obrigatória no Railway\n\nCrie um volume persistente montado em /app/data. Sem esse volume, cada reinicialização perderá o banco e repetirá o backfill.\n\nVariáveis opcionais:\n- PIPELINE_START_DATE: início do histórico da carga inicial; padrão 2024-01-01.\n- ALERT_EMAIL_ENABLED: true somente se as variáveis de e-mail também estiverem configuradas.\n\nO Railway deve estar conectado ao repositório com deploy automático habilitado para a branch main. Cada push aprovado em main gera uma nova imagem.\n\n## Dashboard Streamlit\n\nA API é o serviço principal. Para publicar também o dashboard, crie um segundo serviço Railway apontando para o mesmo repositório, com:\n- start command: streamlit run src/dashboard.py --server.address 0.0.0.0 --server.port $PORT\n- volume montado em /app/data, compartilhando a mesma origem persistente ou uma base PostgreSQL gerenciada.\n\nNão trate duas bases SQLite independentes como se fossem uma única fonte: o dashboard precisa ler exatamente os artefatos produzidos pelo serviço de coleta.\n\n## Critério de aceite\n\nApós o primeiro deploy:\n- /health responde HTTP 200;\n- /docs abre a documentação OpenAPI;\n- /pipeline/health retorna pelo menos uma execução;\n- o arquivo data/processed/financial_data.db existe no volume;\n- um restart do serviço não apaga os dados;\n- a execução das 07:00 aparece no log com Execucao do pipeline finalizada.\n\nA publicação não deve ser considerada concluída sem esses registros.\n
